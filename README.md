# ВышКат — учёт парка кикшеринга

Консольное приложение учёта парка «ВышКат» (КПО, ДЗ №1): доменная модель, SOLID, DI-контейнер (`punq`), юнит-тесты (`pytest`).

## Запуск

Нужен Python 3.10+.

```bash
python -m venv .venv
source .venv/bin/activate         
pip install -r requirements.txt

python -m vyshkat # интерактивное меню
python -m vyshkat --demo # демонстрация всех сценариев без ввода
python -m pytest --cov=vyshkat # тесты + покрытие (~96%)
```

## Что умеет

| Требование из ТЗ | Где в коде |
|---|---|
| Добавление транспорта в парк | `ReceptionService.receive_vehicle` (`services/reception.py`) |
| Техосмотр перед приёмкой (принять/отклонить) | `IServiceCenter` / `ServiceCenter` (`services/service_center.py`) |
| Суммарное суточное потребление энергии | `FleetReports.total_daily_energy_kwh` (`services/reports.py`) |
| Число единиц (всего и по видам) | `FleetReports.total_units`, `units_by_kind` |
| Транспорт для новичков (простота ≥ 6) | `IBeginnerPolicy` / `SimplicityBeginnerPolicy` (`services/beginner_policy.py`) |
| Вещи на балансе + инвентарные номера вместе с техникой | `ReceptionService.register_thing`, `FleetReports.inventory_list` |
| Демонстрация всех сценариев | пункт меню «6» или `--demo` (`console.py`) |

Демо-сценарий показывает: приёмку трёх видов транспорта, отказ техосмотра по износу и по расходу энергии, постановку на баланс шлема, док-станции и зарядного шкафа, затем все отчёты.

## Структура и логика решений

```
vyshkat/
  domain/
    interfaces.py   Inventoried (инвентарный номер), EnergyConsumer (суточный расход)
    base.py         BalanceItem — общая реализация учёта на балансе
    vehicles.py     Vehicle → Bicycle, ElectricScooter, ElectricBike
    things.py       Thing → Helmet, DockStation, ChargingCabinet
  services/
    service_center.py  IServiceCenter, ServiceCenter, InspectionResult
    beginner_policy.py IBeginnerPolicy, SimplicityBeginnerPolicy
    fleet.py           Fleet (хранилище), InventoryNumberGenerator
    reception.py       ReceptionService (приёмка = техосмотр + номер + в парк)
    reports.py         FleetReports (отчёты)
  console.py        ConsoleApp — только ввод/вывод
  container.py      composition root: регистрация зависимостей в punq
  __main__.py       точка входа
tests/              юнит-тесты
```

Ключевые решения:

- **Энергия — это интерфейс, а не поле базового класса.** `EnergyConsumer` реализуют только те, кто реально потребляет энергию (электросамокат, электровелосипед, док-станция, зарядный шкаф). У велосипеда и шлема этого поля нет вообще — не нужно хранить «0 кВт·ч» и не нужно проверять его в отчётах.
- **Инвентарный номер выдаёт система, а не пользователь.** Номер присваивается только при постановке на баланс (`ReceptionService`), один раз (`BalanceItem.assign_inventory_number` запрещает повторное присвоение), а `Fleet.add` не пускает объект без номера. Отклонённый транспорт номера не получает.
- **Сотрудники не наследуют `Inventoried`** — по ТЗ они не ставятся на баланс.
- **Вещи техосмотр не проходят** — по ТЗ техосмотр нужен только для техники.
- **Консоль не содержит бизнес-логики** — она только спрашивает данные и печатает результаты сервисов. Ввод проверяется, поэтому некорректные данные не роняют программу.

## SOLID — где и зачем

- **S (единственная ответственность).** `Fleet` только хранит объекты, `ReceptionService` только принимает, `ServiceCenter` только решает про техосмотр, `FleetReports` только считает отчёты, `ConsoleApp` только общается с пользователем. Поэтому, например, изменение правил техосмотра не затрагивает отчёты и консоль.
- **O (открытость/закрытость).** Новый вид транспорта — это новый класс-наследник `Vehicle` (+ строка в каталоге `VEHICLE_TYPES` для меню). `Fleet`, `ReceptionService`, `FleetReports`, `ServiceCenter` при этом не меняются. Новое правило «для новичков» — новая реализация `IBeginnerPolicy`, без правки отчётов.
- **L (подстановка Лисков).** Любой `Vehicle` можно передать в техосмотр и в отчёты; любой `EnergyConsumer` корректно учитывается в сумме энергии. Подклассы не ослабляют проверки базового класса (простота 1–10, износ 0–100, расход ≥ 0).
- **I (разделение интерфейсов).** Два маленьких интерфейса `Inventoried` и `EnergyConsumer` вместо одного «толстого». Шлем не обязан реализовывать расход энергии, а отчёт по энергии зависит только от `EnergyConsumer`.
- **D (инверсия зависимостей).** `ReceptionService` зависит от абстракции `IServiceCenter`, `FleetReports` — от `IBeginnerPolicy`. Конкретные реализации выбираются в одном месте — `container.py`. Благодаря этому в тестах техосмотр подменяется заглушкой.

**DI-контейнер:** `punq`. Все сервисы регистрируются в `build_container()`; зависимости внедряются через конструкторы по аннотациям типов. `Fleet` и генератор номеров — singleton, чтобы во всём приложении был один парк и одна нумерация.

## Ответы на обязательные вопросы

**1. Какой принцип SOLID применён наиболее явно и где?**
DIP: `ReceptionService` (`services/reception.py`) принимает в конструкторе `IServiceCenter`, а не `ServiceCenter`. Какая реализация будет использована, решает только `container.py`. Именно это позволяет в тестах подменить техосмотр одной строкой `container.register(IServiceCenter, instance=stub)`.

**2. Какой принцип сознательно ограничен / «почти нарушен» и почему это приемлемо?**
- OCP в `ServiceCenter.inspect`: проверка расхода энергии делается через `isinstance(vehicle, EnergyConsumer)`. «Чистое» решение — цепочка отдельных правил техосмотра, но правил всего два, и это был бы overengineering. При росте числа правил их легко вынести в список стратегий.
- Для `InventoryNumberGenerator` и `Fleet` **нет интерфейсов** (DIP «не до конца»): у них одна реализация и подменять их в тестах не нужно (в каждом тесте свой контейнер — свой чистый парк). Интерфейс ради интерфейса — это «декоративный» SOLID.
- Каталог видов в `console.py` (`VEHICLE_TYPES`) при добавлении нового вида нужно дополнить одной строкой — это не бизнес-логика, а описание меню, такая правка допустима.

**3. Что сломается (или не сломается) при расширении?**
- *Новый вид транспорта* (например, моноколесо): класс `Monowheel(Vehicle, EnergyConsumer)` + строка в `VEHICLE_TYPES`. Приёмка, техосмотр (включая проверку энергии), отчёты и инвентаризация заработают без изменений.
- *Сотрудник службы эксплуатации*: отдельный класс, **не** наследующий `Inventoried`/`BalanceItem`, отдельное хранилище. Существующий код не меняется, и сотрудник не попадёт в инвентарную ведомость или сумму энергии — это защищено типами.
- *Склад запчастей*: запчасть — это `Thing` (стоит на балансе, может иметь номер); сам склад — отдельный сервис, зависящий от `Fleet` или своего хранилища. Отчёты продолжат работать. Если запчасти не должны попадать в общий «парк», понадобится отдельное хранилище — это изменение только в новом коде.
- *Другое правило для новичков*: новая реализация `IBeginnerPolicy` и одна строка в `container.py` (пример — в `tests/test_reports.py::test_beginner_policy_can_be_replaced_through_di`).

**4. Какой тест фиксирует решение техосмотра и правило «для новичков»; как подменяется зависимость?**
- `tests/test_reception.py`: `test_accepted_vehicle_gets_number_and_goes_to_fleet`, `test_rejected_vehicle_does_not_get_into_fleet`, `test_reception_always_asks_service_center_mock`. Техосмотр подменяется через DI-контейнер: в `tests/conftest.py` функция `container_with_service_center` берёт **настоящий** контейнер приложения и перерегистрирует `IServiceCenter` заглушкой (`StubServiceCenter`) или `unittest.mock.Mock(spec=IServiceCenter)`. Остальные зависимости остаются реальными.
- Реальные правила техосмотра (износ, расход, граничные значения): `tests/test_service_center.py`.
- Правило «для новичков»: `tests/test_reports.py::test_beginner_rule_threshold_is_six` (граница 5 / 6) и `test_beginner_policy_can_be_replaced_through_di` (подмена политики через контейнер).
